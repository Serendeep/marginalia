# AI for Marginalia without API keys (research, 2026-10-08)

Target: Huawei MatePad TGR-W09 (Kirin 9000WE, 8 GB, Android 12, arm64, no GMS). Mac (Apple Silicon, Ollama) on same Wi-Fi. User has ChatGPT subscription.
Method: web search + fetch of primary docs on 2026-10-08. "UNVERIFIED" marks anything not confirmed from a primary page.

## 1. Using a ChatGPT subscription programmatically

### 1a. NEW: "Sign in with ChatGPT" plan usage (official, announced DevDay 2026-09-29)
- OpenAI now officially lets Plus/Pro subscribers spend plan allowance in third-party apps. Partner list as of 2026-09-30: 12 apps with plan usage (Devin, Warp, Notion, Vercel, Amp...), 4 open-source integrations (OpenClaw, OpenCode, Pi, T3 Code). Source: https://learn.chatgpt.com/docs/sign-in-with-chatgpt ; summary https://flaviocopes.com/sign-in-with-chatgpt/ (secondary); help page https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites (403 on fetch; seen only in search snippets).
- Open-source tools that run on the user's machine need NO OpenAI approval; they self-register on first sign-in. Hosted/commercial apps: selected partners only (interest form). Source: developers landing https://developers.openai.com/siwc (says "ChatGPT plan usage is available to all open-source partners and selected private clients"; flaviocopes secondary for "no approval").
- Mechanics (https://developers.openai.com/siwc/token-sharing-open-source/sign-in):
  - OIDC + PKCE (S256). First registration: `client_id=dynamic_agent_client` + `ext_agent_host_id` + `agent_name_hint`; callback returns an issued `client_id` (`oaiapp_...`) to store per account. No client secret.
  - Redirect URI must be an HTTP loopback on `127.0.0.1` (e.g. `http://127.0.0.1:1455/auth/callback`), not `localhost`; custom schemes not mentioned.
  - Scopes: `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`; `resource=https://api.openai.com/v1`.
  - Token endpoint: `POST https://auth.openai.com/api/accounts/oauth/token`.
- Inference (https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference): `POST https://api.openai.com/v1/responses`, `Authorization: Bearer <access token>`, `store:false`, `stream:true` mandatory. Model list: `GET /v1/models`, keep `visibility=="list"`. Do not use chatgpt.com backend-api.
- Preview limitations (https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations): no `temperature`, `max_output_tokens`, `previous_response_id` (HTTP), system-role items (use `instructions`); no file search, image gen, Code Interpreter, hosted MCP, Files API, audio/video input. Function tools OK; text/images/files OK if model accepts.
- Limits: usage counts against the plan's existing limits; user sets per-app weekly cap; when exhausted requests fail (`subscription_sharing_usage_limit_exceeded`). No numeric rate limits published. Plus: 5-hour window shared across connected apps; Pro: weekly only (flaviocopes, secondary).
- ToS: this is the sanctioned path. Risk = "preview" status; definition of "open-source app" not found (UNVERIFIED whether a public GitHub repo of Marginalia qualifies, or whether `ext_agent_host_id` has allowed values; read "Request a client ID" page https://developers.openai.com/siwc/request-client-id, not fetched).
- Fit: an Android app can run a loopback listener on-device and open the system browser, so tablet-only OAuth looks feasible (UNVERIFIED in practice; needs a browser on the Huawei tablet and the user to be logged in to ChatGPT there). Tablet then calls api.openai.com directly over internet; no Mac needed.

### 1b. Codex CLI "Sign in with ChatGPT"
- Official: Codex supports ChatGPT login (subscription) or API key. Tokens cached in `~/.codex/auth.json` (plaintext, "treat like a password"); auto-refresh. Headless: `codex login --device-auth`. Docs explicitly recommend API keys for programmatic/CI use. Source: https://learn.chatgpt.com/docs/auth (redirect from developers.openai.com/codex/auth).
- Plus limits (UNVERIFIED, secondary, estimates only): ~10-100 local msgs per 5h on GPT-5.6 Sol, more on smaller models; weekly cap on top. Check https://chatgpt.com/codex/pricing/.
- `codex exec` (non-interactive) and Codex app-server (JSON-RPC over stdio; `--listen ws://IP:PORT` websocket; `capability-token` / `signed-bearer-token` auth). app-server and websocket are marked EXPERIMENTAL, "not supported for production workloads"; non-loopback listeners are unauthenticated by default during rollout, so set `--ws-auth`. Source: https://learn.chatgpt.com/docs/app-server. These are agent runtimes (threads, tools), heavier than a chat endpoint; `codex mcp-server` not researched (UNVERIFIED).
- Using Codex as a Mac-side backend with ChatGPT login is supported by OpenAI as Codex usage itself; wrapping it for another app is a gray zone except via 1a.

### 1c. Community proxies (ChatMock etc.)
- ChatMock (https://github.com/RayBytes/ChatMock): `chatmock login` then `chatmock serve`; serves OpenAI-compatible `/v1/responses` (HTTP+WS) and Ollama-compatible endpoints at `http://127.0.0.1:8000/v1`; models auto-discovered from the account; tools, vision, reasoning effort supported. Reuses Codex CLI's OAuth client. README: "Use responsibly and at your own risk", "not affiliated with OpenAI". No rate-limit or ToS statements. Install: brew / pipx / macOS GUI / Docker.
- LAN: only documented via Docker: `CHATMOCK_PUBLISH_HOST=0.0.0.0`, `PORT=8000`, `docker compose up -d chatmock` (https://github.com/RayBytes/ChatMock/blob/main/DOCKER.md). Native bind flag not documented (UNVERIFIED). No auth on the port: anyone on the Wi-Fi spends your quota.
- Other plugins (opencode-openai-codex-auth, GPTMock fork) are the same idea; their READMEs limit use to personal use. Stability: depends on undocumented backend; can break any time. ToS: unofficial; with 1a now available, treat as fallback only. I found no OpenAI statement either permitting or banning them (UNVERIFIED).

### Verdict Q1
"Mac proxy on LAN, tablet calls OpenAI-compatible endpoint" is technically viable but not the best route any more:
- Preferred: implement SIWC open-source flow (1a) in the app; or a tiny Mac-side companion using SIWC tokens and exposing `/v1/chat/completions` on LAN with a bearer token.
- Fallback: ChatMock via Docker on the Mac: `CHATMOCK_PUBLISH_HOST=<mac LAN IP> docker compose up -d chatmock`, `chatmock login` first; tablet base URL `http://<mac-ip>:8000/v1`, any API key string, model from `/v1/models`; cleartext HTTP needs `usesCleartextTraffic` / network security config for that host; firewall must allow 8000. Use `/v1/responses` (documented); `/v1/chat/completions` support not confirmed here.

## 2. On-device LLM without GMS

- LiteRT-LM (successor of MediaPipe LLM Inference): Android supported (CPU/GPU/NPU), Kotlin API stable; docs do not mention Play Services (https://developers.google.com/edge/litert-lm/overview, /android). Maven: `com.google.ai.edge.litertlm:litertlm-android`, latest 0.18.0 on dl.google.com Maven metadata (checked 2026-10-08). minSdk not stated. GPU backend needs `<uses-native-library>` entries for `libOpenCL.so`, `libvndksupport.so` (required=false). API: `Engine(EngineConfig(modelPath))`, `initialize()` (up to ~10 s), `createConversation()`, `sendMessageAsync` returns Flow.
- MediaPipe `com.google.mediapipe:tasks-genai:0.10.27`: "maintenance-only mode", migrate to LiteRT-LM (https://developers.google.com/edge/mediapipe/solutions/genai/llm_inference/android). "Optimized for high-end Android devices such as Pixel 8, S23 or later." Skip for new work.
- Models/sizes/speeds from Google's table (all flagship Snapdragon/Exynos-class; NO Kirin data): Gemma3-1B 1005 MB (int8) / 529 MB int4 QAT .task; S24 Ultra CPU decode 33-55 tk/s, GPU ~24-56. Gemma-3n-E2B 2965 MB, 16 tk/s decode (S24U). Gemma-3n-E4B 4235 MB, 9 tk/s. Gemma4-E2B 2583 MB, 47 tk/s CPU / 52 GPU, ~1.7 GB peak CPU RAM (S26 Ultra). Qwen2.5-1.5B 1598 MB, 34 tk/s. Qwen3-0.6B 586 MB. phi-4-mini 3906 MB, 7 tk/s.
- Kirin 9000WE (Cortex-A77 x4 + A55 x4, Mali-G78 MP24, 2020 silicon): expect roughly 1/3 to 1/2 of S24U CPU numbers => guess 8-20 tk/s for a 1B int4 model, 3-8 for 2B-class. UNVERIFIED; no published Kirin benchmark found. A77 lacks i8mm/SDOT-class improvements of newer cores (SDOT exists on A77); Mali OpenCL GPU path in LiteRT-LM on Kirin is untested. Must benchmark on device.
- Gating/license: Gemma models require accepting Gemma license on Hugging Face (litert-community/Gemma3-1B-IT shows login + agree). Qwen weights are generally Apache-2.0/ungated (UNVERIFIED for specific litert-community conversions). Ship by user-initiated download or sideload, not bundled; model download needs HF token for gated repos.
- llama.cpp: official `examples/llama.android` Kotlin binding (`AiChat`/`InferenceEngine` Flow API), arm64 CPU, KleidiAI optional; GGUF model zoo large (Qwen3, Gemma 3, Llama 3.2). No Maven artifact; vendored source + NDK build (https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md). Most model choice, no GMS, no gating for many models; you own the native build.
- MLC LLM: needs real mobile GPU (OpenCL/TVM), demo targets Snapdragon 8 Gen 2, heavy build (Rust, NDK, TVM), demo APK dated 2024-09; maintenance of Android SDK not stated. Skip.
- ONNX Runtime GenAI: Android listed but Maven artifact/NNAPI not confirmed on its README (https://github.com/microsoft/onnxruntime-genai); CPU only for this device. Skip.
- Recommendation (on-device LLM): LiteRT-LM with Gemma3-1B-IT int4 (or Qwen2.5-1.5B) via CPU backend, GPU as optional benchmark. Fallback if LiteRT-LM misbehaves on Kirin: llama.cpp binding + Qwen GGUF Q4_K_M. 8 GB is ample for 1-2B; avoid E4B/phi-4-mini (single-digit tk/s on much faster chips).
- Quality caveat: 1B-class models are weak for Q&A over PDFs and flashcard quality; fine for short summaries/explanations.

- OCR: ML Kit text recognition v2 has a bundled variant `com.google.mlkit:text-recognition:16.0.1` (Latin, ~4 MB/arch, model linked into the app; scripts: `-chinese`, `-devanagari`, `-japanese`, `-korean`) vs unbundled `play-services-mlkit-text-recognition` (needs GMS) (https://developers.google.com/ml-kit/vision/text-recognition/v2/android). - For PDFs with a text layer, OCR is unnecessary; extract text with PDF library first.
- Embeddings: MediaPipe Text Embedder `com.google.mediapipe:tasks-text` (docs updated 2026-08-17, no Play Services mention, no model list on the page; https://developers.google.com/edge/mediapipe/solutions/text/text_embedder/android). LiteRT-LM overview lists EmbeddingGemma 2 Text (270M) at 165 MB, text embed ~27 ms on S26U CPU (hardware-bound; expect ~3-5x slower on Kirin, still fine for batch indexing). Gemma license applies. Simpler alternative for "Q&A over PDF": BM25/FTS5 keyword retrieval, no embeddings.

## 4. Ranked shortlist

1. Sign in with ChatGPT (official open-source token sharing) -> OpenAI Responses API, direct from tablet or via a Mac companion. Only route that uses the subscription with OpenAI's blessing and gets frontier-quality summaries/flashcards/PDF Q&A with no Mac dependency. Costs: build OIDC+PKCE loopback flow, adapt to Responses API quirks (stream-only, `store:false`, no `temperature`), dependent on a preview program and on Marginalia qualifying as "open-source" (check the Request-a-client-ID page first; make the repo public if needed). Usage draws on Plus limits with a user-set weekly cap.
2. Mac-hosted OpenAI-compatible endpoint on LAN (ChatMock in Docker, or Ollama on the Mac for fully local/free models) behind one configurable "base URL + model" setting. Fastest to build (the app only needs an OpenAI/Ollama-style client; ChatMock exposes both), works whenever the Mac is awake on the same Wi-Fi. ChatMock = unofficial and quota-sharing risk (open port, no auth); Ollama on the Mac (e.g. Qwen3/Gemma 3 at 8-14B) has no ToS issue and no quota, quality below frontier. Recommend building this client abstraction first since it also backs option 1 and 3.
3. On-device LiteRT-LM (Gemma3-1B-IT int4 / Qwen2.5-1.5B), offline fallback for short summaries and "explain this". No GMS dependency documented, no network, no quota; limited quality, user must accept Gemma license / download 0.5-1.6 GB, and Kirin speed is unmeasured. Use llama.cpp binding if LiteRT-LM GPU/CPU path fails on Kirin.
